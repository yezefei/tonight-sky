## 0. 一句话范围

**第一期后端只做两件事：把链接里的内容搬到服务端（短链），把「回音到了」送到用户手里（订阅消息）。**

账号体系、数据云同步都往后排。原型已验证的原则不变：不做广场、不做陌生人匹配、不做任何公开内容池——后端不存在"信息流"这种东西，这从根本上决定了架构可以非常轻。

## 1. 现状与问题

| 现状（原型） | 问题 | 后端解法 |
|---|---|---|
| 送星/晚安卡内容 base64 编码在 URL hash 里（`#star=` `#card=` `#reply=`） | 链接上千字符，微信转发被折叠截断，打开率受损；内容无法做安全审核 | 内容入库，链接只带 8 位短 ID |
| 回复抵达靠发送方自己再点链接 | 对方回复了，发送方根本不知道，关系链路断掉 | 微信订阅消息触达 |
| 数据只存 localStorage | 换手机/清缓存即丢失；「夜空是资产」的留存逻辑不成立 | 第二期云同步（见 §7） |
| 星回（30 天回看作答）纯本地计时 | 本地可触发，但用户不打开就永远不知道 | 订阅消息提醒（候选，谨慎） |

## 2. 技术选型建议

- **微信小程序 + 云开发（云函数 + 云数据库）**。理由：团队成本最低；免自建服务器和域名备案走 HTTP API 的复杂度；订阅消息、内容安全接口都是一等公民；第一期数据模型简单，文档型数据库完全够用。
- 若未来需要复杂查询或迁移，再迁到自建（Node + PostgreSQL），本文档的 API 形状保持不变即可。

## 3. 数据模型

### 3.1 `stars`（星星/心事记录）—— 第二期云同步才需要，第一期不落库

```
{
  _openid: String,        // 云开发自动带
  id: Number,             // 客户端生成的毫秒时间戳，保持与原型一致
  tag: String,            // 工作/感情/金钱/家庭/未来/说不清，可空
  text: String,           // 原文，加密存储（见 §6.2）
  x: Number, y: Number,   // 夜空坐标（百分比）
  done: Boolean,          // 已翻篇（金星）
  sent: Boolean,
  reply: String,          // 收到的回复
  more: [{ t, text }],    // 星回续写
  snoozed: Number,        // 星回"再放一会儿"的时间戳
  createdAt: Number,
  updatedAt: Number
}
```

### 3.2 `shares`（分享载体）—— 第一期核心

```
{
  _id: String,            // 短 ID，8 位 Crockford base32（无歧义字符），如 "7k3m9x2q"
  type: 'star' | 'card',  // 送星 / 晚安卡
  from: String,           // 发送方 openid
  payload: {
    text: String,         // type=star：心事原文（加密）
    style: String,        // type=card：卡片样式 star/letter/moonsea
    lineIdx: Number       // type=card：文案序号
  },
  reply: String,          // 接收方回复（加密），可空
  status: 'waiting' | 'opened' | 'replied' | 'expired',
  openedAt: Number,
  repliedAt: Number,
  createdAt: Number,
  expireAt: Number        // createdAt + 30 天，过期清理
}
```

索引：`_id`（唯一）、`from + createdAt`、`expireAt`（TTL 清理）。

### 3.3 `subscriptions`（订阅消息授权记录）

```
{
  _openid: String,
  scene: 'reply_arrival' | 'star_opened' | 'revisit',
  shareId: String,        // 仅 reply/star 场景；revisit 场景为空
  createdAt: Number
}
```

微信订阅消息是**一次授权发一条**，所以每次用户点「送出」「等待回音」都要重新请求授权，授权记录即待发送队列。

## 4. API（云函数）

全部走云函数，入参出参 JSON。错误统一 `{ code, message }`。

### 4.1 `share.create` —— 生成分享链接

```
入: { type, payload: { text?|style+lineIdx? } }
出: { shareId, path }     // path = pages/receive/receive?id=7k3m9x2q
```
- **先过内容安全检测**（`security.msgSecCheck`），不过则返回委婉错误：「这句话里有些内容星星带不走，换种说法试试？」——不告诉具体原因，符合产品「不评价」气质。
- 写库后返回短链，前端拼小程序卡片分享（`onShareAppMessage`），不再是复制长链接。

### 4.2 `share.open` —— 接收方打开

```
入: { shareId }
出: { type, payload, status }
```
- 原子更新 `status: waiting → opened`，记录 `openedAt`。
- **若发送方订阅了 `star_opened` 通知，触发发送**：「你送出的那颗星，被打开了。」
- 过期/不存在：`{ code: 'GONE' }`，前端走原型已有的「这颗星星迷路了」兜底。

### 4.3 `share.reply` —— 接收方回复

```
入: { shareId, text }
出: { ok: true }
```
- 内容安全检测同上。
- 更新 `status → replied`，写 `reply`。
- **触发 `reply_arrival` 通知给发送方**：「你送出的那颗星，有回音了。」
- 通知里**不带回复内容**，只带入口——内容只在小程序内看，兼顾隐私和打开率。

### 4.4 `notify.subscribe` —— 登记一次订阅授权

```
入: { scene, shareId? }
出: { ok: true }
```
- 前端在「生成送星链接」「收下这颗星」等动作后调 `wx.requestSubscribeMessage`，成功一个 scene 落一条。

### 4.5 `revisit.notify`（候选，第二期评估）

星回提醒：「一颗 30 天前的星，在等你回头看看。」
风险：这是唯一一条「非事件触发的主动推送」，最接近骚扰。**建议第一期不做**，先看用户自然回访数据；若做，频率上限每 7 天一条，深夜（23:00–6:00）可发——这正是目标用户醒着的时间，但需 A/B 验证。

### 4.6 第二期：`stars.sync` —— 夜空云同步

```
入: { stars: [...] }      // 全量或增量（按 updatedAt）
出: { stars: [...] }      // 服务端合并结果
```
- 合并策略：以 `id` 为主键，`updatedAt` 新者胜。删除用墓碑标记（`deletedAt`）保留 30 天。
- 登录即同步；本地始终是全量副本，离线可用，弱网无感。

## 5. 关键流程时序

### 5.1 送星 → 回音（第一期核心链路）

```
发送方                    云函数                   接收方
  |  写心事 → 送星          |                       |
  |----share.create------->| msgSecCheck            |
  |<---shareId-------------| 入库 shares            |
  |  requestSubscribeMessage(reply_arrival, star_opened)
  |----notify.subscribe--->| 落授权队列              |
  |  转发小程序卡片给 TA     |                       |
  |                        |<----打开卡片------------|
  |                        |----share.open--------->|
  |<==订阅消息「被打开了」====| status→opened          |
  |                        |<---回复-----------------|
  |                        |----share.reply-------->|
  |<==订阅消息「有回音了」====| status→replied         |
  |  打开小程序看回复        |                       |
```

### 5.2 星回（本地优先，通知后置）

完全复用原型逻辑：`!done && now - (snoozed||t) > 30d` → 首页出现横幅与金色光晕星 → 回看作答三选一（翻篇/再放/续写）。后端唯一可能的角色是 §4.5 的提醒，且默认不做。

## 6. 安全与合规

### 6.1 内容安全（红线，不过不能上线）

- 所有 UGC 文本（心事、回复）入库前必须过 `security.msgSecCheck`；图片（用户未来的自定义卡片）过 `imgSecCheck`。
- 注意原型当前是单机，**没有内容审核**——这是 hash 原型与正式版之间最大的合规差距，不是可选项。
- 微信小程序 UGC 类目要求：需要「社交-笔记」或相应类目资质，上架前按《开发交接文档》§9.1 的资质清单逐项核验。

### 6.2 隐私

- 产品承诺「没人会看到」——心事与回复**服务端加密存储**（AES-256-GCM，密钥放云环境变量，或更进一步用客户端派生密钥、服务端零知识，但会牺牲找回能力，第一期建议前者）。
- 分享链接 30 天过期，过期物理删除。
- 用户删除星星（「熄灭」）→ 服务端同步物理删除，不留回收站。
- 订阅消息只发事件、不带内容（见 §4.3）。

### 6.3 边界声明

产品已去除危机干预页。需法务确认：纯私密记录 + 定向分享（无广场、无推荐）形态下，平台是否仍负有危机内容处置义务；若有，最轻方案是在内容安全检测命中自伤类别时，返回固定关怀文案 + 援助热线（不存储、不上报）。

## 7. 分期计划

| 期 | 内容 | 验收标准 |
|---|---|---|
| **一期（2-3 周）** | 云开发工程；`shares` 三张 API + 订阅消息；msgSecCheck 接入；送星/收星/回复全链路小程序化；前端从 hash 协议切到短链 | 两台真机互送星，回音通知 1 分钟内到达；长文不再被截断 |
| **二期（2 周）** | 微信登录；`stars.sync` 云同步；换机恢复 | 新设备登录后夜空完整还原，含金星与续写 |
| **三期（评估后）** | 星回订阅消息；年度星空图服务端渲染；付费（晚安卡样式/星空装扮，虚拟支付走 iOS 合规通道） | 各指标见下 |

### 一期埋点（配合北极星指标）

- 写完率、放它走完成率（留存主漏斗）
- 送星率、打开率、回复率（裂变质量）
- 通知→回访率（订阅消息的真实效果）
- 30 日星回查看率、星回→翻篇率（北极星指标的直接驱动）

## 8. 成本量级（云开发）

按 1 万 DAU 估算：云函数调用 + 数据库读写 + 短信级订阅消息免费额度内，**月成本在百元级**。第一期没有图片存储（卡片全 canvas 前端生成），没有带宽压力。这个产品可以很长时间保持极低成本运行——这是它作为「健康小生意」的底层优势。

## 9. 不做清单（防止范围蔓延）

- 不做用户资料页/头像/昵称系统（匿名是气质）
- 不做评论、点赞、关注（任何社交图谱都禁止）
- 不做推荐算法、不做热榜（没有内容池，自然不需要）
- 不做积分/等级（违反设计原则第 5 条「无压力」）
- 第一期不做 iOS/Android 原生 App（小程序验证完后用 Taro/原生重写再议）
